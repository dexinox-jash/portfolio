02 · The bet

Why I picked this fight.

Four short answers to the four questions every project should be able to answer before the first commit.

Signal

The gap is structural, not cosmetic.

The minimalist launcher market splits into two failure modes: iOS widgets that are static text lists with no intelligence, and Android launchers that are either too bare or too expensive ($24/year subscriptions). Nobody offers context-aware mode switching + mindful friction + one-time pricing.

Filter

Solo-buildable in bounded time.

Defensible by architecture: zero server costs, zero data compliance overhead, zero third-party dependencies. Revenue model legible in one sentence. Differentiated by behavior, not just aesthetic.

Why now

Digital wellness has moved from fringe to mainstream.

Post-pandemic screen-time awareness, Apple's Screen Time normalization, and the "dumb phone" trend all point to the same demand. The window is open now because incumbents are subscription-fatigued or technically shallow.

Why me

Self-interest, properly executed.

I catch myself unlocking my phone to do one thing and losing twenty minutes. The mindful-gate idea — a five-second breathing pause before Instagram — is exactly what I would install on my own device.

03 · No-jargon explainer

Problem. Solution. Result.

01 · Problem

Smartphones are attention-extraction machines by design.

The home screen is the front door — covered in notification badges, color-saturated icons, and infinite scroll feeds. Existing "minimalist" solutions are either too passive (static lists that don't adapt) or too predatory (subscriptions that monetize the same anxiety they claim to solve). Users who genuinely want focus are underserved by both extremes.

02 · Solution

Replace the home screen entirely.

Context-aware modes auto-switch the visible app list by time and day — work apps at 9 AM, personal apps at 5 PM, wind-down apps at 9 PM. Mindful gates add configurable friction before distracting apps: a breathing pause, an intention prompt, or a ten-second delay. A focus-score algorithm gives objective feedback on daily phone habits. One-time purchase, no subscription, no data collection, no network calls.

52 files, 26 unit tests (all passing), 0 compile errors, debug and release (R8) builds green. All 3 critical and 6 major audit findings remediated. Remaining gaps are pre-launch admin (signing keystore, privacy policy URL, Play Console listing) — not engineering. iOS WidgetKit companion planned for v2.0.

04 · My process

How I got here without burning millions of tokens.

Four habits, applied recursively. The same discipline that kept the build cheap also kept it correct.

01 · Spec-first constraint setting

The 1,355-line spec was written before a single line of Kotlin.

Every feature, every data model, every schedule-conflict rule, every focus-score deduction was decided in prose first. This isn't waterfall; it's constraint-setting. Once the spec locks the behavior, the code becomes almost mechanical. The interesting decisions happen upstream.

02 · Scoped agents per phase

Phase 1 (spec) → Phase 2 (build) → Phase 3 (audit) → Phase 4 (remediation) → Phase 5 (regression).

Each phase's output is the next phase's input, and nothing else. Cross-phase leakage is how bugs survive. Three parallel discovery agents scanned compliance in the audit phase. Fix agents were scoped to critical/major/minor tiers. The validation agent re-ran the full test matrix.

03 · Knowledge graph as working memory

The vault rendering this page tracked the spec, the audit, the changelog, and the shipping docs.

A new session picks up the relevant subgraph (e.g., just "audit findings + remediation status") as prefix context. The graph is the working memory; the agent is the foreground process.

04 · Token efficiency as a value

Spec-first saved the most tokens.

Re-prompting "what should the focus score formula be?" across three agents would have been expensive and inconsistent. Writing it once in the spec, then referencing by section number, made every downstream agent self-consistent for free. The audit ran overnight for less than a senior engineer's hourly rate.

08 · Engineering proof

One artefact. One decision moment.

Including this exhibit because the interesting part isn't the syntax — it's that an automated audit caught a broken alarm chain before a user woke up on day two. That's a process bet, not a coding skill.

EXHIBIT · DECISION · RELIABILITY IS A FEATURE

When the alarm fires, the next alarm must already be set.

The first audit caught a major bug: ModeTransitionReceiver broadcasted a UI refresh when an alarm fired, but never re-scheduled the next alarm. Mode transitions worked on day one, then silently stopped. The fix wasn't complex — one suspend function call — but the interesting part is the decision it encodes: a launcher that auto-switches modes is only as reliable as its alarm chain. Breaking that chain breaks the core value proposition.

Before 
private fun handleModeTransition(
  context: Context, intent: Intent
) {
  val refresh = Intent(
    "com.everlauncher.REFRESH_MODE"
  )
  context.sendBroadcast(refresh)
  // Chain breaks here
}
After 
private suspend fun handleModeTransition(
  context: Context, intent: Intent
) {
  val refresh = Intent(
    "com.everlauncher.REFRESH_MODE"
  )
  context.sendBroadcast(refresh)
  // Re-arm next 24 hours
  scheduleUseCase.scheduleNext24Hours()
}
09 · Deep dive — Focus Score Algorithm

The mirror, deconstructed.

Closed-form arithmetic over eight integer fields. No loops, no network calls, no ML. Deterministic, testable, and explainable — the opposite of a black-box wellness score.

The formula

Base 100. Capped deductions. Capped bonuses. Clamped 0–100. The caps are the editorial decisions — they prevent any one bad habit from destroying the score.

// base
score = 100

// deductions (capped)
score -= min(unlocks × 1, 30)
score -= min(bypasses × 2, 20)
score -= min(overrides × 5, 15)
score -= min((screenTime − 3h) / 15min, 20)

// bonuses (capped)
score += min(phoneFreeStreaks × 3, 15)
score += focusCompleted ? 10 : 0
score += noGatesOpened ? 5 : 0

// clamp
score = clamp(score, 0, 100) 
fun calculateFocusScore(
  today: DailyAnalytics
): Int {
  val deductions = min(today.unlocks, 30)
    + min(today.gatedBypasses * 2, 20)
    + min(today.modeOverrides * 5, 15)
    + max(0, (today.screenTime - 180) / 15)
    .coerceAtMost(20)
  val bonuses = min(today.phoneFreeStreaks * 3, 15)
    + if (today.focusCompleted) 10 else 0
    + if (today.noGatesOpened) 5 else 0
  return (100 - deductions + bonuses)
    .coerceIn(0, 100)
}

The seven threshold rules. Each one named, each one bounded.

The cap value is the editorial decision. Picking 30 for unlocks, 20 for bypasses, 15 for overrides — these are the calls that make the score feel fair instead of punitive.

01

Phone unlocks

Each unlock costs 1 point. Capped at 30. More than 30 unlocks in a day is already its own signal.
−1 · max 30
02

Gated app bypasses

Opening an app that has a gate costs 2 points. Capped at 20. The gate is meant to create awareness; bypassing it is the behavior being measured.
−2 · max 20
03

Mode overrides

Manually switching out of a scheduled mode costs 5 points. Capped at 15. Three overrides a day is already a pattern worth noticing.
−5 · max 15
04

Screen time over 3 hours

Every additional 15 minutes beyond 3 hours costs 1 point. Capped at 20. The 3-hour baseline is the editorial guess at a "reasonable" day.
−1/15min · max 20
05

Phone-free streaks

Every 30-minute streak without touching the phone earns 3 points. Capped at 15. Five such streaks = a genuinely focused day.
+3/30min · max 15
06

Focus hours completed

Completing all scheduled focus mode hours earns a flat +10. This is the largest single bonus — the system rewards adherence to your own plan.
+10
07

No gated apps opened

A flat +5 bonus if no gated apps were opened all day. Small but meaningful — it rewards the days when friction wasn't even tested.
+5
▸ Why closed-form arithmetic, not an ML model

An ML model would pick up the same patterns — but at the cost of opacity, training data, and device-side inference complexity. Eight integer fields plus arithmetic runs in microseconds, produces explainable outputs, and requires zero network calls. The tradeoff is generality for transparency, and for a wellness score the right side wins every time.

11 · Decisions

Five questions worth answering.

Strategic first, technical last. The technical decisions are downstream of the strategic ones.

01
Why a full launcher replacement instead of an overlay app?
+
An overlay can be dismissed. A launcher is the default. The commitment level of replacing the home screen is the product's core signal.
Android allows CATEGORY_HOME apps to fully replace the home screen — back button becomes no-op, home button always returns here. An overlay or accessibility-service approach would be easier to build but easier to ignore. The product's value proposition is behavioral change, and behavioral change requires commitment.
02
Why sell externally instead of in-app purchase?
+
No payment gateway code, no billing SDK, no 30% store commission on direct sales. The business model and the privacy stance are the same document.
In-app billing would require Google Play Billing Library, server-side purchase validation, and account infrastructure. External sales (Amazon, eBay, direct website) shift fulfillment to platforms that already handle it, keep the APK free of payment code, and let the user own the app outright. For a privacy-first product, "no billing code in the app" is a feature.
03
Why three gate types instead of one?
+
Different users need different friction. A student might need the delay gate for TikTok; a knowledge worker might need the intention gate for email.
Breathing (passive, 5s) is for mild habit-breaking. Intention (active, requires typing) is for apps you open reflexively without purpose. Delay (passive, 10s) is for apps you know you shouldn't open but do anyway. Offering all three with per-app configuration lets the user calibrate their own friction. The default is breathing — the gentlest intervention.
04
Why audit before any user testing?
+
A launcher that crashes or loses alarms is worse than no launcher at all — the user can't easily fall back to their old home screen.
System-level apps have a higher reliability bar than utility apps. If a to-do app crashes, the user opens it again. If a launcher crashes, the user is stranded. The 5-phase build treated reliability as a first-class feature. The audit found 15 issues; fixing them before launch was cheaper than recovering from negative reviews.
05
Why defer iOS to v2.0?
+
iOS cannot replace the home screen — it can only provide a widget. The product shape is fundamentally different on iOS.
Apple's WidgetKit approach is a different product than an Android CATEGORY_HOME launcher. The context-aware mode switching, the gates, and the launcher search all need rethinking for widget constraints. Shipping Android first validates the core behavior and revenue model; v2.0 ports the validated concept rather than betting both platforms on an unproven design.

13 · Reflection

What surprised me. What I'd change. What's next.

What surprised me

The audit found things my intuition didn't.

The alarm-chain bug (modes stopping after day one) was invisible in manual testing because I never left the emulator running for 24 hours. The hidden-app count hardcoded to zero made the feature appear to work while being completely broken. Automated audit caught both. Senior-engineer-grade verification is now solo-builder-accessible.

What I'd do differently

Ship an internal alpha to 3 real users before the audit.

The audit found technical issues; real users would have found experiential ones. The mode-editing UI (sliders, chips, checkboxes) is correct but untested by anyone who isn't me. One afternoon of user observation would have de-risked the interaction design.

What's next

v1.1 tests. v1.2 icons. v2.0 iOS.

Compose UI tests + integration suite. Custom app icons. iOS WidgetKit companion — the spec is already written, porting a validated concept is faster than inventing one. v2.1: location-based mode switching. The second platform is the proof; the third is the pattern.
