Most budget apps are spreadsheets, surveillance, or both.

This one is neither. The web version notices when you're spending weird before you do — but the math runs on your laptop, not in someone's data warehouse. The mobile version doesn't even know there's an internet.

Six closed-form detectors plus OLS regression. No LLM round-trip.

Cross-platform: Expo SDK 54 + RN 0.81 + expo-sqlite + Reanimated v4 (mobile); React 19 + Vite 7 + Tailwind 4 + framer-motion + recharts + react-window + vite-plugin-pwa (web). The "no data leaves the device" promise is enforced at the storage layer — every layer above inherits the constraint.

02 · The bet

Why I picked this fight.

Four short answers to the four questions every project should be able to answer before the first commit.

Signal

The intersection was empty.

Every budget app I tried was a spreadsheet your accountant cried over, or surveillance dressed in fintech glow. The intersection of "beautiful" and "won't sell my data" was conspicuously empty.

Filter

Solo-buildable in 8 weeks.

Defensible privacy stance (legible to a non-engineer in one sentence). Dual-platform reach. Recurring engagement (a budget you check once is a budget that didn't work).

Why now

Two trends, same calendar.

Privacy concerns and AI-insight demand are growing on the same curve. Most apps do one well, the other badly. Doing both, on-device, gets harder to ship the longer you wait for someone else to do it.

Why me

I'd be the first user.

I track my own budget. I know which features I'd never use because no other app trusted me enough to put the math where I could see it. I wanted to write the version that wasn't a euphemism.

03 · No-jargon explainer

Problem. Solution. Result.

01 · Problem

The category sorts into two failure modes.

Spreadsheet-with-extra-steps — accurate, configurable, hostile to anyone whose job isn't accounting. Or AI-powered surveillance — friendly UI, free tier, business model is your transaction history. Both treat the user as either a power user to be tolerated or a product to be sold.

02 · Solution

Ship the same brand twice.

Different ergonomics, same data model, same Dark Romance theme, same 15 emoji-categories. Native mobile for the daily flow (two-tap entry, on-device SQLite). Web for the analysis (charts, predictions, browser-local data). Six on-device detectors instead of an LLM round-trip. Subscription monetization so the business model and the privacy stance don't fight each other.

03 · Result

Both shipped. Both audited. Both honest.

Mobile v2.0 Stable on TestFlight — 23+ documented bugs hardened, SQLite migration system. Web live at everbudget-85930.web.app — automated functional test reports 23 / 26 passes, 0 console errors, TTFB ~1ms, DOM ~20ms. WCAG 2.1 AA accessibility audit produced a 12-fix implementation guide. Four bugs surfaced and logged with reproduction steps rather than quietly redeployed.

04 · My process

How I got here without burning the budget I was tracking.

Four habits, applied recursively. The same discipline that kept user data on the device kept the build cheap.

01 · Thinking in three loops

Strategic, then tactical, then execution. In that order.

Most builders skip the first. I write it first, then let it constrain everything downstream — including which features get cut. The "no LLM in the insight engine" decision is downstream of "no data leaves the device," which is downstream of "this is the budget app I'd recommend to my mother." The decision tree isn't deep, but it's enforced.

02 · Scoped agents per domain

The mobile agent never sees web context.

Each loop has a vocabulary the next loop respects. Audit agent never sees implementation; the writer agent (the one generating this manifest) only sees what the analysis agent already structured. Cross-domain leakage is the leading cause of token waste.

03 · Knowledge graph as working memory

The vault rendering this page is the same vault that designed EverBudget.

The Obsidian graph at vault/ stores design decisions, audit findings, schema migrations across both products. New session = re-load the relevant subgraph as prefix context, not re-explain the project from zero. The graph is the working memory; the agent is the foreground process.

04 · Token efficiency as a value

Heuristics-not-LLM, applied recursively.

Use closed-form math wherever possible. Prefix-load only the relevant subgraph. Validate against schema before sending to the next agent — the harness's Validator catches 80% of follow-up rounds before they happen.

06 · Stakeholder lens

Five perspectives I held at the same time.

A solo builder is also their own product manager, business person, ops lead, legal scout, and growth marketer. Each lens left fingerprints on the design.

Customer

I want to see my money. I don't want to be the product. I want it on my phone and my laptop because I check both. I'll pay if you don't sell my data — but only if I can tell, in one sentence, why you couldn't sell it even if you wanted to.

Business

Subscription via App Store on mobile + Stripe on web. Freemium hook: local-only is free; AI insights are paid. Cost-of-goods is roughly flat (no per-user cloud) so margin scales linearly with subs. Future ceiling: B2B angle — credit unions wanting to white-label the privacy story.

Operations

Solo, no team to scale. The privacy stance doubles as ops simplifier — no per-user data warehouse, no GDPR data-subject-access pipeline, no analytics vendor invoices. Firebase free tier + Supabase as opt-in to defer the "do I have customers yet" question.

Legal & Privacy

GDPR by architecture, not by policy. Data on device means no transfer to disclose, no DPA to sign, no Schrems-II cross-border problem. Apple privacy nutrition label is mostly empty checkboxes. Provable, not just claimed.

Growth

Shareable insight cards as low-cost referral mechanic ("saved $X this month — 3 detectors fired"). Apple Health / Google Fit as future income-side integration. B2B credit-union pilot would validate the playbook.

EXHIBIT · PROCESS · AUDIT CAUGHT IT BEFORE A USER DID

When the AI tried to divide hope by reality.

Automated functional testing on March 6 caught a high-severity bug in the web app's AI chat: four call sites computed percentages by dividing totalSpent / totalBudget with no zero-check. New users (no budget set yet) got 'NaN%' and 'Infinity%' splashed across the chat. Cost of audit: a weekend. Cost of any one of those bugs reaching a user in fintech: probably the user.

09 · Deep dive — structured thinking

The insight engine, deconstructed.

Six named detectors, explicit thresholds, closed-form math. The structure is the demo — naming each detector with its trigger condition is what makes the product explainable instead of mystical.

OLS, the unglamorous backbone

Standard univariate ordinary least squares. Closed-form, microseconds, good enough for monthly totals.

// slope (β) and intercept (α)
β = Σ ( xi − x̄ )( yi − ȳ ) ÷ Σ ( xi − x̄ )²
α = ȳ − β · x̄

// forecast next month
forecast = α + β · ( n + 1 ) 
function predictNextMonth(history) {
  const n = history.length;
  if (n < 3) return history[n-1]?.total ?? 0;
  const xs = history.map((_, i) => i);
  const ys = history.map(h => h.total);
  const xBar = mean(xs), yBar = mean(ys);
  const beta = sum(xs.map((x, i) =>
    (x - xBar) * (ys[i] - yBar)
  )) / sum(xs.map(x => (x - xBar) ** 2));
  const alpha = yBar - beta * xBar;
  return alpha + beta * n;
}

The five threshold detectors. Each one named, each one bounded.

The threshold value is the editorial decision. Picking 40% for category dominance, 1.5σ for unusual spending — these are the calls that make the engine feel curated instead of generic.

Unusual spending

Micro-expense aggregation

Surfaces small frequent purchases that quietly add up — 18 × $4 coffees = $72 you didn't budget for. group by merchant where amount < $10, sum monthly

04

Weekend spike

Compares Sat/Sun average daily spend against Mon–Fri average. Flags when weekend exceeds weekday by >50%. (weekend_mean / weekday_mean) − 1 > 0.5
Δ > 50%
05

Category dominance

Alerts when any single category exceeds 40% of monthly spend, signaling lifestyle imbalance. max(category_total) / month_total > 0.40
share > 40%
06

Monthly trend delta

Compares this month's running total against the average of the last three closed months. delta = (current − avg(last_3)) / avg(last_3)
|Δ| > 20%
▸ Why heuristics, not an LLM

An LLM would pick up the same patterns — but at the cost of streaming every transaction to a third party. Six O(n) algorithms run client-side, produce explainable outputs, and don't require a privacy disclaimer. The LLM tradeoff is generality for confidentiality, and for finance the right side wins every time.

11 · Decisions

Five questions worth answering.

Strategic first, technical last. The technical decisions are downstream of the strategic ones — that's the order they were made and the order they should be read.

01
Why this market, and why now?
+
Privacy concerns and AI-insight demand are converging. Most apps do one well, the other badly.
Two trends meeting on the same calendar: post-Cambridge-Analytica baseline distrust that no longer requires the user to be a privacy nerd, and people now expecting an app to notice things about their data. Most fintech in this category picks one and loses the other. Solo build, dual-platform, ~8-week budget: tight enough to ship, loose enough to do both halves well.
02
Why two platforms instead of one?
+
Different ergonomics. Mobile is for input. Web is for analysis.
One codebase serving both flows produces a mobile UI cluttered with charts and a web UI awkwardly thumb-sized. The strategic risk wasn't "too much work" — it was "one product that does neither thing well." React Native + Expo for the input loop, React + Vite for the analysis loop, shared data model and design language. The web's insight engine is the one part neither platform shares — it's there because the web is where you'd actually look at it.
03
Why ship two products solo instead of one with co-founders?
+
Marginal cost of the second product was small. Co-founder overhead would have been larger.
EverBudget's mobile and web builds share the schema, the categories, the theme, and the brand voice. The cost of the web build, given the mobile work was already done, was ~30% additional calendar time — versus probably 3× the management overhead of bringing in a co-founder for what's a single product strategically. The tradeoff is real; on a different bet (B2B sales-led) I'd reverse it.
04
Why audit before launch instead of letting users find the bugs?
+
Fintech is the wrong category to ship-and-iterate. The first NaN% in front of a user is the last user.
A NaN% in a meal-planner app is a bug; in a budget app it's a credibility event. The functional + WCAG audit on March 6 caught 4 bugs (1 critical, 2 high, 1 medium) — every one would have been a user-facing failure. Cost of audit: a weekend. Cost of any one of those bugs reaching a user: probably the user.
05
Why heuristics instead of an LLM in the insight engine?
+
Because user transactions shouldn't go to OpenAI to find out their coffee budget is high.
Six O(n) detectors plus closed-form OLS regression run client-side, produce explainable outputs, and don't require a privacy disclaimer. The LLM tradeoff is generality for confidentiality, and for finance the right side wins every time. Plus: deterministic outputs make the test suite trivial.
12 · Journey

Five phases, with what each one taught me.

PHASE 01
Foundation — what to make impossible
DETERMINED

Started with the constraints, not the features. Wrote down the rules: local storage, no telemetry, two surfaces, one design language, ship something users open more than once. The constraints did most of the design work. What I learned: writing the negative-space first makes the feature decisions almost mechanical.

Project scaffolding · Dark Romance theme spec · 15-category emoji language · explicit list of what NOT to build

PHASE 02
Mobile v1.1 — the version that taught me what was wrong
PRAGMATIC

First mobile build on Expo + Redux-Persist. ~20 known bugs by the time it ran end-to-end. What I learned: Redux-Persist couldn't carry a non-trivial schema, and "we'll add a real database later" is the kind of decision that sets next-quarter you on fire. v1.1 wasn't wasted — it was the version that made the v2.0 case obvious.

v1.1 · basic transaction tracking · Redux-Persist · honest list of ~20 bugs

PHASE 03
Mobile v2.0 — the rewrite I wished I'd done first
SURGICAL

Migrated storage from Redux-Persist to expo-sqlite. Numbered migrations, thread-safe singleton, Repository Pattern. Hardened 23+ bugs in the same pass. New visual pass with Reanimated v4 and a particle splash. What I learned: the schema-and-storage decision is the load-bearing wall of every fintech app; getting it wrong in v1 is paid back at compounding interest in v2. Worth it anyway.

v2.0 Stable · production-ready mobile build · EAS profile for TestFlight + Android APK

PHASE 04
EverBudget AI (Web) — the analytical mirror
AMBITIOUS

Brought EverBudget to the browser with a different brief: less data entry, more analysis. Built the heuristic insight engine — six detectors plus OLS regression, all client-side. Shipped as an installable PWA. What I learned: the web is where users look at their data; the mobile is where they capture it. Designing for the right verb per platform was the design unlock.

Live deploy at everbudget-85930.web.app via Firebase Hosting · vite-plugin-pwa

PHASE 05
Audits — the weekend that paid for itself
HONEST

Two automated audits in one day. Functional test caught 1 critical, 2 high, 1 medium bug. WCAG 2.1 AA audit shipped a 12-fix implementation guide. What I learned: the audit is the cheapest senior engineer you'll ever hire. Every bug it caught would have been a user-facing failure in a category where the first failure is often the last user.

13 · Reflection

What surprised me. What I'd change. What's next.

What surprised me

The audit found things my intuition didn't.

NaN%, missing routes, Firestore composite indexes — every one of these I would have shipped and learned about the hard way. Senior-engineer-grade auditing tools are now solo-builder-affordable. Not using them is a process choice, not a cost choice.

What I'd do differently

Ship one platform first, then build the second.

The dual-platform bet was correct strategically, but it cost calendar time I could have spent listening to actual humans. The product probably wouldn't have changed; the order would have.

What's next

Patch four. Wire one. Pilot one.

Fix the four audit findings. Wire Apple Health / Google Fit for income-side ingestion. Test the B2B angle with one credit-union pilot — privacy-narrative is their gap, captive audience is mine.
